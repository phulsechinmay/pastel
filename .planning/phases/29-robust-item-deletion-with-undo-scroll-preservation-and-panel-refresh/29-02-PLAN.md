  <name>Task 1: Add soft-delete exclusion, slide-left transitions, Cmd+Z undo, and selection advancement to FilteredCardListView</name>
  <files>Pastel/Views/Panel/FilteredCardListView.swift</files>
  <action>
**Access DeletionManager:**
- Add `@Environment(AppState.self) private var appState` (if not already present, or use existing environment).
- Derive `deletionManager` from `appState.deletionManager` for convenience.

**Remove deletionCount parameter:**
- Remove `var deletionCount: Int` stored property.
- Remove the `deletionCount` parameter from `init(...)`.
- Remove the `.onChange(of: deletionCount)` handler entirely.

**Exclude soft-deleted items in computeFilteredItems:**
- At the TOP of `computeFilteredItems(from:)`, before the sync filter, add:
  ```swift
  let softDeleted = appState.deletionManager.softDeletedIDs
  let nonDeleted = items.filter { !softDeleted.contains($0.persistentModelID) }
  ```
  Then use `nonDeleted` instead of `items` for the rest of the pipeline.
- Add an `.onChange(of: appState.deletionManager.softDeletedIDs)` handler that recomputes `filteredItems` (same as the existing `onChange(of: items)` pattern). This ensures the list updates when an item is soft-deleted or undo restores it.

**Add slide-left removal transition:**
- On each card view in the `ForEach` (in the `cardView(for:at:)` helper or directly in the ForEach body), add:
  ```swift
  .transition(.asymmetric(
      insertion: .opacity,
      removal: .move(edge: .leading).combined(with: .opacity)
  ))
  ```
- The `withAnimation(.easeOut(duration: 0.2))` wrapper is already applied in ClipboardCardView.deleteItem() (from Plan 01), so the transition will animate automatically when the item disappears from the ForEach.

**Add Cmd+Z to NSEvent keyboard monitor:**
- In `installKeyboardMonitor()`, add a case before the `default:` catch-all:
  ```swift
  case 0x06: // kVK_ANSI_Z
      if event.modifierFlags.contains(.command) && !event.modifierFlags.contains(.shift) {
          withAnimation(.easeOut(duration: 0.2)) {
              appState.deletionManager.undo()
          }
          return nil // consumed
      }
      return event
  ```
- This restores the soft-deleted item (pendingDeletion becomes nil, softDeletedIDs becomes empty, computeFilteredItems re-includes the item). Per user decision, restored item appears at top of list (it already will, since items are sorted by timestamp descending and the item retains its original timestamp).

**Selection advancement after deletion:**
- The selection advancement needs to happen when an item is soft-deleted. Since ClipboardCardView calls `softDelete` with `withAnimation`, the `computeFilteredItems` will rerun via the `onChange(of: softDeletedIDs)` handler. After recomputation, check if `selectedIndex` is still valid:
  ```swift
  .onChange(of: appState.deletionManager.softDeletedIDs) { _, newIDs in
      filteredItems = computeFilteredItems(from: items)
      // Advance selection after deletion
      if let idx = selectedIndex, idx >= visibleItems.count {
          selectedIndex = visibleItems.isEmpty ? nil : visibleItems.count - 1
      }
  }
  ```
  This handles: if deleted item was last, select new last; if deleted item was in middle, same index now points to next item (shifted up), which is the correct "select next below" behavior.

**Important anti-patterns to avoid:**
- Do NOT add `deletionManager.softDeletedIDs` to the `.id()` modifier on FilteredCardListView in PanelContentView. This would cause full view recreation, destroying scroll position -- the exact problem we are solving.
- Do NOT use `.animation()` on the view itself. Use `withAnimation {}` wrapping the state change (already done in ClipboardCardView.deleteItem from Plan 01).
  </action>

- No other changes needed — DeletionManager is accessed via `@Environment(AppState.self)` inside FilteredCardListView, not passed as a parameter.

**PanelController.swift (PanelActions class):**
- Remove `var deletionCount = 0` from the `PanelActions` class. This property is no longer used by any view.

**PanelController.swift (scroll position memory):**
- The user wants scroll position remembered across panel dismiss/reopen cycles. The ScrollPosition API approach from the research is ideal but complex to thread through. A simpler approach that still satisfies the requirement:
  - In FilteredCardListView, the `@State private var scrollPosition` is already local view state. When the `.id()` on FilteredCardListView changes (on panel reopen via showCount), the view is recreated and scroll state is lost.
  - **Solution:** The `.id()` already includes `showCount` which causes recreation on each panel show. To preserve scroll position across dismiss/reopen, we need to NOT include `showCount` in the `.id()`. However, `showCount` serves the purpose of refreshing the @Query when the panel opens.
  - **Revised approach:** Instead of relying on `.id()` changes for refresh, use an `.onAppear` + `.onChange(of: panelActions.showCount)` combination to trigger `filteredItems` recomputation without view recreation. This is the same pattern already used for `deletionCount`.
  - In PanelContentView, change the `.id()` modifier on FilteredCardListView to only include search text and label IDs (remove `showCount`):
    ```swift
    .id("\(debouncedSearchText)\(selectedLabelIDs.sorted(by: { "\($0)" < "\($1)" }).map { "\($0)" }.joined())")
    ```
  - Add a new `var showCount: Int` parameter to FilteredCardListView's init (replacing the removed `deletionCount`), and add an `.onChange(of: showCount)` handler that recomputes filtered items and resets displayLimit. This triggers a data refresh without view recreation.
  - Actually, even simpler: FilteredCardListView already has `.onChange(of: items)` which fires when @Query re-fetches. The @Query will re-fetch when its predicate changes. Since the predicate includes search text (via the `.id()` recreating the view with new init params), and the panel reopen scenario means the same search text... We need some mechanism to refresh.
  - **Final approach:** Keep `showCount` in FilteredCardListView as a parameter (renamed from `deletionCount`). On `.onChange(of: showCount)`, recompute filteredItems and reset displayLimit to initial page size. This handles panel reopen refresh. The `.id()` in PanelContentView drops `showCount` so the view is NOT recreated on reopen, preserving scroll position. The data refresh happens via onChange handler instead.

  Concretely in FilteredCardListView:
  - Add `var showCount: Int` parameter (replaces `deletionCount`).
  - In `.onChange(of: showCount)`:
    ```swift
    .onChange(of: showCount) { _, _ in
        displayLimit = pageSize
        filteredItems = computeFilteredItems(from: items)
        selectedIndex = nil
    }
    ```

  In PanelContentView:
  - Pass `showCount: panelActions.showCount` instead of `deletionCount: panelActions.deletionCount`.
  - Change `.id()` to exclude showCount:
    ```swift
    .id("\(debouncedSearchText)\(selectedLabelIDs.sorted(by: { "\($0)" < "\($1)" }).map { "\($0)" }.joined())")
    ```

  This preserves scroll position across dismiss/reopen while still refreshing data.

**Key constraint:** The search text and label filter changes should still trigger view recreation (`.id()` changes) to get a fresh @Query. Only showCount (panel toggle) should NOT cause recreation, so scroll survives dismiss/reopen.
  </action>
